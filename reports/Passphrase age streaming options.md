# Upstream blocks force passphrase pivots

**pyrage will not deliver streaming passphrase `encrypt_io`/`decrypt_io` on any predictable timeline**, so plan-4’s assumption that upstream contribution closes the multi-GB gap is no longer a workable dependency. The Rust `age` crate already streams scrypt-wrapped payloads; the gap is only woodruffw’s Python binding surface, and on [pyrage#172](https://github.com/woodruffw/pyrage/issues/172) the maintainer stated a preference against growing that surface further. Five families of options remain viable under this package’s constraints (stock `age -d` recovery where possible, bounded memory, passphrase never on argv, no VCS deps in published metadata, keep existing recipient `encrypt_io`): own a thin PyO3 passphrase binder (or fork), shell out to FiloSottile **age ≥1.3** with **`age-plugin-batchpass`** and `AGE_PASSPHRASE_FD`, adopt a young pure-Python stock-v1 streamer (`python-age` or `age-rt.AgeEncoder`), or amend the product UX so multi-GB dumps use recipients (or a passphrase-wrapped identity) while sole-scrypt content stays out of scope. Waiting on stock PyPI pyrage alone is high-risk and open-ended. This report evaluates those paths for a decision; it does not recommend implementing any of them yet.

## Rage already streams; pyrage will not

pyrage **1.4.0** already ships recipient **`encrypt_io` / `decrypt_io`** (and path helpers) that copy through rage’s streaming encryptor, which is why ADR-0003’s recipient path works for multi-GB dumps today ([pyrage lib.rs](https://raw.githubusercontent.com/woodruffw/pyrage/main/src/lib.rs); [PR #77](https://github.com/woodruffw/pyrage/pull/77)). The **`pyrage.passphrase` module exposes only one-shot `encrypt`/`decrypt` that buffer full plaintext and ciphertext into memory** ([passphrase.rs](https://raw.githubusercontent.com/woodruffw/pyrage/main/src/passphrase.rs); [PyPI pyrage](https://pypi.org/project/pyrage/)). That is not a missing crypto primitive: the Rust `age` crate’s `Encryptor::with_user_passphrase` plus `wrap_output` / `StreamWriter` already produce stock scrypt-stanza age v1 files with STREAM chunking ([docs.rs Encryptor](https://docs.rs/age/latest/age/struct.Encryptor.html); [age-encryption.org/v1](https://age-encryption.org/v1)). pyrage’s passphrase path wraps those APIs and then collects into a `Vec`.

Issue **#172 remains open with no commitment**. woodruffw closed and locked PR #171 (spam / LLM authorship), then wrote that at a high level **he does not want to add more streaming APIs** because they are hard to get right, while still asking what problem the requester is solving ([#172 comment](https://github.com/woodruffw/pyrage/issues/172#issuecomment-6317197865); [PR #171](https://github.com/woodruffw/pyrage/pull/171)). After a human clarification about multi-GB WordPress backups, there was no further maintainer reply as of 2026-10-25. Recipient streaming itself was hard-won earlier (#36 → #77 → v1.2.0), and recent posture on #168 favors internal buffer tweaks over new public knobs ([#36](https://github.com/woodruffw/pyrage/issues/36); [#168](https://github.com/woodruffw/pyrage/issues/168)). **Waiting for a PyPI release that adds `passphrase.encrypt_io` is therefore months-to-indefinite**, acceptance-gated rather than packaging-gated. Any follow-up upstream attempt would need an explicit “in scope” signal and clearly human authorship; treat merge as optional luck, not a sprint floor.

## Own the binding or keep a short-lived git pin

Licenses allow ownership: **pyrage is MIT** and the Rust **`age` crate is MIT OR Apache-2.0**, so a fork or a new binding can be published under a different distribution name if copyright notices are retained ([pyrage LICENSE](https://raw.githubusercontent.com/woodruffw/pyrage/main/LICENSE); [crates.io/age](https://crates.io/crates/age)). The code delta for passphrase IO is small and mechanical—mirror recipient `encrypt_io` with `Encryptor::with_user_passphrase` / `scrypt::Identity`, as the closed ravensorb branch did ([fork passphrase.rs](https://raw.githubusercontent.com/ravensorb/pyrage/passphrase-encrypt-io/src/passphrase.rs)). **A thin dedicated PyO3/maturin crate that only exposes streaming passphrase encrypt/decrypt** is the cleanest publishable ownership shape: published metadata can pin a normal version (compatible with `uv build --no-sources`), recipient/SSH streaming stays on stock `pyrage`, and rebase tax is limited to the passphrase path rather than the whole SSH/plugin/x25519 surface. A full public fork under a new PyPI name is also legal but inherits the entire upstream maintenance and wheel matrix. Private **Gitea-only** wheels fit temporary staging but conflict with later public-PyPI consumers and invite dependency-confusion if the distribution name collides with woodruffw’s `pyrage` ([Gitea PyPI docs](https://docs.gitea.com/usage/packages/pypi/)).

ctypes/cffi to the rage **binary** reintroduces the secret-channel and subprocess problems ADR-0003 already rejected; rage documents the Rust `age` crate—not a C ABI—as the library API ([str4d/rage](https://github.com/str4d/rage/)). Vendoring patched wheels inside this repo freezes security updates and fights multi-arch abi3 packaging. **Git-pinning a fork under `[tool.uv.sources]` remains valid for development only**; it cannot appear in published metadata. Whoever owns a compiled binder must watch `age` crate bumps and cut new wheels—stock pyrage will not refresh an embedded fork. Upstream manylinux wheels exist for common glibc Docker bases; **musllinux is absent from pyrage 1.4.0 on PyPI**, so Alpine WordPress images need an explicit matrix or in-image compile for any owned binding too ([pypi 1.4.0 JSON](https://pypi.org/pypi/pyrage/1.4.0/json); [maturin distribution](https://www.maturin.rs/distribution.html)).

## Batchpass reopens CLI streaming with packaging cost

ADR-0003 and plan-4 correctly rejected **stock `age -p`**: core passphrase mode remains **TTY-interactive only**, with no argv/env flags on the main binary ([FiloSottile/age](https://github.com/FiloSottile/age); closed [PR #520](https://github.com/FiloSottile/age/pull/520)). That absolute rejection no longer holds for the **automation path introduced in age v1.3.0**: the separate **`age-plugin-batchpass`** invoked as `age -e -j batchpass` / `age -d -j batchpass`, reading **`AGE_PASSPHRASE` or `AGE_PASSPHRASE_FD`**—never argv ([v1.3.0 release](https://github.com/FiloSottile/age/releases/tag/v1.3.0); [batchpass man](https://man.archlinux.org/man/extra/age/age-plugin-batchpass.1.en)). The plugin wraps stock `ScryptRecipient` / scrypt unwrap, so ciphertext stays a normal sole-scrypt age file recoverable with interactive `age -d` without the plugin ([plugin source](https://raw.githubusercontent.com/FiloSottile/age/main/cmd/age-plugin-batchpass/plugin-batchpass.go)). Empirically, age **v1.3.2** streamed a 50 MiB pipe round-trip under batchpass with exact byte recovery; age’s STREAM design uses **64 KiB** chunks for bounded payload memory ([FiloSottile/age#176](https://github.com/FiloSottile/age/pull/176)).

**Prefer `AGE_PASSPHRASE_FD` over env** from Python `subprocess` (`pass_fds`, minimal `env`, no `shell=True`): argv remains forbidden; environ is better than argv but still same-UID visible and inherits into both `age` and the plugin process ([Security SE guidance](https://security.stackexchange.com/questions/190071/when-running-shell-scripts-is-it-safer-to-pass-sensitive-information-using-stdi); batchpass man warning on shell history). Official Go release tarballs for **v1.3.2** already ship `age-plugin-batchpass` beside `age` for linux/darwin/windows; many distro packages still lag (local Ubuntu was still **1.2.1** without the plugin). The plugin must be on **`$PATH` as `age-plugin-batchpass`**, not merely next to the `age` binary. **rage does not add a better native passphrase automation flag**; maintainers defer to the same batchpass plugin ([rage#617](https://github.com/str4d/rage/pull/617); [rage#550](https://github.com/str4d/rage/issues/550)). Kassiber’s prior art still splits CLI streaming for recipients and in-process pyrage for passphrase—largely because pre-batchpass subprocess passphrase was unsafe—so a CLI pivot is a **viable architecture with two binaries, PATH wiring, and weaker secret hygiene than in-process bindings**, not a free lunch ([kassiber age_cli.py](https://github.com/bitcoinaustria/kassiber/blob/7bf8dbbc/kassiber/backup/age_cli.py)).

## Pure-Python streamers and UX pivots that keep age

Among PyPI age implementations, **genuine incremental STREAM for stock passphrase** appears in **`python-age`** (`encrypt_file` / stream helpers, ~64 KiB chunks) and **`age-rt`’s `AgeEncoder`/`AgeDecoder`** (default 65536; avoid unofficial `AgeRTEncoder`, which is not stock-compatible) ([PyPI python-age](https://pypi.org/project/python-age/); [PyPI age-rt](https://pypi.org/project/age-rt/); [C2SP age](https://c2sp.org/age@v1.1.0)). Authors claim Go `age` interoperability for the stock paths; this research did not re-run live multi-GB `age -d` cross-tests. Both are young and low-visibility (**0 stars**; `python-age` 0.1.0; `age-rt` unaudited by design disclaimer). jojonas **`age`/pyage buffers entire payloads** despite a file-like API, carries open stock-passphrase decrypt bugs, and is effectively abandoned since 2023—unsuitable ([jojonas/pyage#14](https://github.com/jojonas/pyage/issues/14); [PyPI age](https://pypi.org/project/age/)). **`age-rt` is passphrase-only** (cannot replace pyrage for X25519/SSH). **`python-age` covers X25519 + scrypt streaming** but not SSH, and installs top-level module `age`, colliding with jojonas if both appear. A coexistence pattern is **stock pyrage for recipient/`encrypt_io` + SSH, plus `age-rt` or `python-age` only for passphrase streams**, accepting maturity and audit risk versus owning Rust bindings.

Architecture pivots that **avoid passphrase streaming APIs entirely** still keep the age format. Age’s scrypt stanza **must be the only recipient**; mixing scrypt with X25519 in one header is forbidden ([C2SP age](https://c2sp.org/age); [scrypt.go](https://github.com/FiloSottile/age/blob/main/scrypt.go)). The documented workflow is **passphrase-encrypt a small identity** (`age-keygen | age -p > key.age`), then **`encrypt_io` the multi-GB dump to that X25519 recipient**; operator recovery is `age -d -i key.age dump.age`, not bare `age -d dump.age` ([FiloSottile/age README](https://github.com/FiloSottile/age)). That matches how restic/borg/kopia/duplicacy wrap a small key blob under a passphrase KDF and stream content under separate keys—they do **not** run the passphrase KDF over multi-GB payloads ([restic design](https://github.com/restic/restic/blob/master/doc/design.rst); [Kopia encryption](https://kopia.io/docs/advanced/encryption/)). Custom one-file envelopes (tar of key+data, tar-of-age-chunks, hand-rolled STREAM) break single-invocation stock recovery or reinvent crypto ADR-0003 rejected. **Recipients-only for multi-GB** (refuse content `passphrase=` above a memory budget) is the lowest engineering risk relative to pyrage friction but **amends plan-4’s sole-scrypt `age -d` story** and needs ADR/backup AD-26 alignment. Switching to GPG, SOPS, or agebox is high cost: ADR-0003 chose age for streaming + stock CLI + no keyring, and those alternatives either reintroduce rejected deps or target structured secrets rather than dump pipes ([ADR-0003](../docs/adr/0003-age-encryption.md)).

## Conclusion

The decision is no longer “when does pyrage land passphrase IO?” but **which constraint to spend against which cost**: ownership of a thin Rust binder (publishable pin, wheel CI, security update duty), host/vendored **age+batchpass** (FD plumbing, PATH, distro lag), young pure-Python streamers (maturity/audit), or an **ADR UX amendment** that keeps multi-GB on recipients/`encrypt_io` and treats passphrase as identity wrapping—or drops content passphrase until something else changes. Upstream wait is the only option that spends **calendar uncertainty** instead of engineering; given the maintainer’s stated stance, that spend buys little certainty. What changed since plan-4 is not the age format or rage’s capability—it is that **batchpass made CLI automation conditionally real**, pure-Python stock streamers appeared as immature alternatives, and **woodruffw closed the assumed contribution path**, so sole-scrypt multi-GB in Python is now an ownership or product-scope problem rather than an upstream patch ticket.
